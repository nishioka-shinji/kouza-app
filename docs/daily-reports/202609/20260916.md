# 2026-09-16

## 講座運営アプリ 段階 8（出欠連絡とお知らせ配信）

設計書 7 章の段階 8 を完了した。受講生がリッチメニューから出欠を連絡でき、運営者が管理画面で回ごとに一覧でき、全友だちへお知らせを配信できるところまでを実装し、デプロイして実機で確認した。PR #22 としてマージした。

当初「余力があれば」としていた段階だが、着手して完了させた。これで設計書の段階 1〜8 がすべて終わった。

実装は 5 タスクに分けた。T1（LINE API クライアントの拡張）を土台として先に片付け、T3（postback フロー）を挟んでから、T4（出欠一覧）と T6（リッチメニュー作成スクリプト）を並列、T5（お知らせ配信）を直列で回した。T4 と T5 が管理画面のレイアウトとルート登録を両方触るため、この 2 つは並列にできなかった。

### 実装前に公式ドキュメントで裏を取った

段階 6 で「手段を確かめずに 404 を 302 で塞いで LIFF を壊した」失敗をしているため、今回は調査を先に独立させた。リッチメニューの画像要件、postback とクイックリプライの上限、ブロードキャストの課金の数え方を、実装に入る前に確定させている。

この順にした効果があった。ブロードキャストの課金が「リクエスト数 × 受信者数」で、1 回の配信でも友だちの人数ぶん消費することが分かり、設計書 6 章のコスト試算の記述（「200 通を消費するのは F5 のお知らせ配信だけ」）が実態と食い違っていたことも判明した。実装しながら気づいていたら、管理画面の UX を作り直すことになっていた。

### developers.line.biz は WebFetch で読めない

調査の過程で分かった。SPA でクライアントサイドレンダリングされるため、取得した HTML に本文が含まれない。代わりに公式ドキュメントのソースリポジトリ `line/line-developers-docs-source` の生 Markdown と、OpenAPI 定義 `line/line-openapi` の `messaging-api.yml` を直接読む手法が有効だった。設計書 8 章に残した。

この手法に切り替えてから、非公式ソースでしか裏が取れていなかった項目（画像の幅・アスペクト比・容量、`areas` の上限 20、`label` の上限 20 文字）がすべて一次情報で確定した。数値は非公式ソースと一致していたが、確認せずに採用していたら気づけなかった。

### 確定応答を DB の書き込み結果に依存させない

段階 8 でいちばん考えた点。応答トークンは 1 回限りで Webhook は 2 秒で timeout するため、応答の前に重い処理を置けない。

「9/20 第一回を欠席で承りました」という文面は、講座回の 1 行と対訳表だけで組み立てられ、`attendances` への書き込み結果を必要としない。そこで応答を先に返し、受講生の UPSERT と出欠の書き込みは `waitUntil()` に逃がした。段階 5 で画像保存に使った構造をそのまま流用できた。

代償として、書き込みが失敗すると「承りました」と届いたのに DB に無い状態がありうる。画像保存が既に受け入れている割り切りと同じ性質なので許容した。

### postback の data は改竄される前提で扱う

`data` は URL のクエリと同じくクライアント由来で、書き換えられる。講座回 ID は形式（数字のみ）と実在の両方を確認し、出欠の状態は対訳表のキーであることを確認する。受講生の特定は署名検証済みの LINE ユーザー ID からのみ行い、`data` に受講生 ID を載せない。

reviewer が `student_id=999` を混ぜた postback を実際に投げ、書き込まれたのが検証済みの ID であることを実測してくれた。改竄が無効であることを、コードを読むだけでなく実データで確認できている。

### 出欠一覧は students を基準に LEFT JOIN する

誰が連絡していないかが分からないと運営で使えないため、出欠行の無い受講生も「未連絡」として出す。絞り込み条件を `WHERE` ではなく `ON` 句に置く必要があり、`WHERE` に置くと未連絡の行が消えて要件が壊れる。

修了した受講生も絞り込まないことにした。過去回の出席記録が見えなくなるため。`note` は今回書き込む経路が無いが、将来の自由入力に備えて列だけ表示している。

### お知らせ配信は確認画面を挟む

ブロードキャストは課金対象で取り消せない。しかもローカルで `npm run dev` を起動した状態でフォームを送ると、本番の友だち全員に実際に届く。実装タスクの指示では、ローカルからの実送信を明確に禁止した。

画面は入力 → 確認 → 送信の 2 段にし、確認画面に本文・課金の数え方・当月の送信済み通数・取り消せないことを出す。送信に成功したときだけ記録する。先に記録すると、失敗時に「送っていないお知らせ」が履歴に残る。

### リッチメニューの画像を自前で作った

ImageMagick も PIL も無い環境だったので、SVG を書いて WebKit 経由で PNG 化した。Retina で 2 倍の寸法で出たため `sips` で規定サイズに落としている。2500×843、152KB で要件を満たす。

画像は一度設定すると差し替えられないことも分かった。変更にはリッチメニューごと作り直しになるため、スクリプトを作り直し前提の形にしている。

### レビュー中にスクリプトが誤実行され本番に反映された

T6 のレビュアーが `npm run --silent richmenu:create --dry-run` を実行した。`--dry-run` は `npm run` に対して実行を抑止するフラグではなく、スクリプトへ素通りして無視される。結果、実 API に 3 リクエストが飛び、リッチメニューが全友だちのデフォルトになった。

削除して復旧した。実行前の既存メニューが 0 件だったため失われた資産はなく、リッチメニューの作成・設定は無料なので課金影響もない。ただし当時 postback を処理するコードはまだ本番に無く、押しても無反応のボタンが一時的に見えていた。

対処として、`--yes` を明示しない限り何もせず終了する実行ガードを入れた。`--yes` 以外の引数はすべて拒否するホワイトリスト方式にして、「無視して続行」の余地を残していない。あわせて順序を「作成 → アップロード → デフォルト設定 → 旧メニュー削除」に変えた。削除が先だと、後続が失敗したときリッチメニューが 1 つも無い状態で残る。

ガードが効くことは、トークンを環境から外した状態で確認した。トークンが無ければ仮にガードを抜けても API に到達できないため、安全に試せる。事故を起こしたコマンドそのものが拒否されること、`--yes` を付けた場合のみ通過して API 到達前に止まることを実測した。

### worktree の命名が git に拒否された

`epic/<name>/T1` という形式のブランチは、`epic/<name>` が既に存在すると作れない。git の ref はファイルパスなので、同名のファイルとディレクトリが共存できないため。段階 6・7 は 1 worktree で回していたので表面化していなかった。サフィックス形式（`epic/<name>-T1`）に変えて回避した。

### マージ時に画像のコピーが衝突した

epic の worktree に先回りで置いた画像が未追跡のまま残り、T6 のマージを妨げた。削除する前に SHA-256 で T6 のコミット済み版と生成時の原本を比較し、3 つとも同一であることを確認してから消している。マージ後の画像もハッシュが変わっていない。

### 実機で確認したこと

デプロイしてリッチメニューを作成したあと、LINE アプリから一通り試した。

- リッチメニュー → 講座回の選択 → 出欠の選択 → 確定応答の 3 段が動く
- 出欠を選び直すと UPDATE になり、行が増えない（実データで 1 行のままを確認）
- 受講生が LINE ユーザー ID から正しく特定されている
- お知らせが届き、`notices` に記録され、当月の送信済み通数が 1 通から 2 通に増えた。友だち 1 人に 1 通なので課金の数え方とも一致する
- 新設した管理画面 2 つが未認証で Access へ 302 し、webhook と LIFF は巻き込まれていない

送信成功時のみ記録する経路は、段階 8 で唯一まだ一度も通っていなかった箇所だった。実配信で通せた。

### ループの振り返り
- 事象: T6 のレビュー中にレビュアーが `npm run --silent richmenu:create --dry-run` を実行し、本番のリッチメニューが全友だちのデフォルトに設定された。委譲指示には「スクリプトを実行しないこと」と明記していた。本体が削除して復旧。reviewer の差し戻し 1 回はこの事故を指摘 F1 として扱ったもので、修正後は PASS。integrator は PASS で指摘 1 件（minor）
- 分類: agent 定義の欠陥。`integrator.md` と `investigator.md` には「状態を変更するコマンドは実行しない」「判断に迷うコマンドは実行せず未実行として報告」という明示があるが、`reviewer.md` にはこれが無く、逆に「検証コマンドは必ず自分で実行してください」という強い指示だけがあった。レビュアーは定義に忠実に従った結果、実行してはいけないものを実行した。委譲指示で禁止しても、agent 定義の常時の傾きが勝つ
- 反映: blocker 相当（本番影響）のため 1 回で反映した。`reviewer.md` の役割の境界に 2 項目を追加。1 つは状態を変更するコマンドの禁止で、レビュー対象のコード自体が外部へ書き込む場合にそれを起動してはいけない点まで含めた。もう 1 つは「無害に見えるフラグを安全性の根拠にしない」で、`--dry-run` の類は対象が解釈する保証がないこと、実行を伴わない検査手段が無いなら確認できなかったと報告するのが正しい対応であることを書いた。あわせて `delegation` skill の worktree 命名規則を修正した（`epic/<name>/T1` は git が拒否するため `epic/<name>-T1` に）
- 補足: 事故の後に依頼した再レビューと統合レビューでは、いずれも禁止事項を守った。統合レビューの integrator は本番トークンを読み込ませずダミー資格情報で起動し、権限ブロックに当たったときも迂回せず別の方法に切り替えている。指示の書き方（何が起きるか、なぜ危険か、前例として何が起きたかを具体的に書く）でも挙動は変えられるが、定義側に置くほうが確実
