# 2026-09-14

## 講座運営アプリ 段階 3（D1 スキーマと管理画面）

設計書 7 章の段階 3 を完了した。D1 に 5 テーブルを作り、受講生と講座回を登録・一覧できる管理画面を `/admin` 配下に実装し、デプロイ先で動作を確認した。PR #7 としてマージ済み。

D1 データベースは `kouza-app-db` を APAC に作成し、バインディング名は wrangler の提案（`kouza_app_db`）ではなく `DB` にした。設計書と CLAUDE.md の記述が `c.env.DB` 前提で、コード中で短いほうが読みやすいため。

マイグレーションは 5 テーブルを 1 本にまとめた。段階 3 で画面を作るのは `students` と `lessons` だけだが、`images` と `attendances` の外部キーが両者を参照し、SQLite では `ALTER TABLE` で外部キーを後から追加できずテーブル再作成になる。器だけ先に作っておく。

### status を英語で格納する

設計書 5 章は「受講中／修了」「出席／欠席／遅刻」と日本語で書いているが、これは表示にあたるものと解釈し、DB には `enrolled` / `completed`、`present` / `absent` / `late` を入れて CHECK 制約で縛った。SQL とコード中に日本語リテラルが散るのを避けるため。対訳表は 1 箇所に集約した。

CHECK 制約と対訳表は値の集合を一致させる必要があり、片方だけ増やすと実行時に CHECK 違反で 500 になる。その旨をコメントに残した。

### 認証を段階 7 から段階 3 へ前倒しした

当初の計画では認証は段階 7 だったが、段階 3 でデプロイまで通すなら認証のない管理画面が公開 URL に出てしまう。受講生の LINE ユーザー ID と表示名が読める状態になるため、この段階で入れることにした。

Basic 認証と Cloudflare Access を比較し、Access を採った。Basic 認証は認証情報が毎リクエスト平文で飛び、MFA もログアウトもなく、総当たりに対して自前のレート制限が要る。Access ならアプリ側にコードも資格情報も持たずに済み、習得目的（Cloudflare の主要機能に触れる）にも沿う。Hono のミドルウェアを書く練習は失われるが、段階 6 の LIFF ID トークン検証で取れる。

ID プロバイダーは One-time PIN にした。Google を IdP にすると GCP でのプロジェクト作成と OAuth クライアント作成が要るが、One-time PIN なら設定不要でメールアドレスの指定だけで済む。Zero Trust は既に有効化済みで、チーム名は `gke-zero-cost`、プランは Free（50 ユーザーまで）だった。

### Access で保護するパスの切り分け

宛先に `/admin` と `/admin/*` の 2 件を登録した。Cloudflare のパス指定では `/admin/*` が `/admin` 自身を覆わないため、1 件だけだと管理画面のトップが無防備に残る。

`/webhook` と段階 6 の LIFF・画像配信は保護してはいけない。LINE プラットフォームからの POST と受講生の LINE アプリ内ブラウザが認証画面へリダイレクトされ、機能しなくなる。同じ理由で Workers ダッシュボードの「Protect this Worker behind Access」も使っていない。これは Worker に紐づく全ドメイン（routes、Custom Domain、workers.dev、プレビュー）をまとめて保護してしまう。

デプロイ後に各パスを確認し、`/` が 200、`/webhook` が 404、`/admin` と `/admin/students` が Access のログイン画面へ 302 になることを確かめた。ログイン後に受講生と講座回を 1 件ずつ登録し、本番 D1 に行が入ることも確認した。

ローカル開発では Cloudflare を経由しないため Access が効かない。管理画面の保護はデプロイ先でしか確認できない。

### 入力値の検証はアプリ側に置く

レビューで、HTML の `required` はクライアント側にしか効かず、フォームを介さない POST では素通りすることが指摘された。`NOT NULL` も空文字を弾かない。結果として空文字の氏名や不正な `status`、実在しない日付が保存される経路が残っていた。

`held_on` は形式（`YYYY-MM-DD`）の一致だけでは足りない。`2026-02-30` のような日付が通ってしまうため、`Date` で UTC 正規化して往復比較する方式にした。この値は段階 6 の講座回選択の基準になるので、壊れた日付が入ると後段の並び順と絞り込みが狂う。

### 申し送り

動作確認のため本番の `students` にテスト行（`Utest-stage3`）を 1 件入れてある。LINE の実ユーザー ID ではないので、段階 5 で実 ID の行を作るときに削除する。設計書にも残した。開発者自身は友だち追加済みで follow イベントが飛んでこないため、段階 5 では実 ID の行を別途作る必要がある。

段階 4 の LIFF はエンドポイント URL として同じドメインのサブパスを充てることになる。そのパスを Access の保護対象に含めてはいけない。現状の保護対象は `/admin` 配下だけなので、`/liff` などを選べば衝突しない。

`wrangler d1 create` の初回実行が認証エラー（code: 10000）で失敗した。トークンのスコープには `d1 (write)` があり権限は足りていたので、OAuth トークンの期限切れだった。`wrangler login` で再認証して解決した。

## 講座運営アプリ 段階 4（LIFF の調査と設定）

設計書 7 章の段階 4 を完了した。LIFF の初期化手順を公式ドキュメントで確認し、LINE Login チャネルと LIFF アプリを作成、エンドポイント URL に疎通確認ページを当てて実機で開けることを確かめた。PR #9 としてマージ済み。

### LIFF アプリは Messaging API チャネルに追加できない

設計書の前提が 1 点崩れていた。LIFF アプリは LINE Login チャネル（または LINE MINI App）にしか追加できず、段階 1 で作った Messaging API チャネルとは別のチャネルを作る必要があった。両者は同じプロバイダー配下に置き、LINE Login チャネル側で公式アカウントに紐づけた。

影響が出るのは F2 の ID トークン検証で、`client_id` に渡すのは LINE Login チャネルの ID になる。設計書は「LIFF アプリのチャネル ID」という曖昧な書き方だったため、取り違えないよう明記した。段階 6 でここを誤ると検証が通らず、原因をコード側で探すことになる。

段階 4 を独立させて Webhook より前に置いた判断が効いた。段階 6 で実装しながらこれに当たっていたら、自分のコードの誤りと設定の不足を切り分けられなかった。

### エンドポイント URL は /liff に当てた

Cloudflare Access の保護対象が `/admin` と `/admin/*` の 2 件だけなので衝突しない。受講生の LINE アプリ内ブラウザから開くパスを Access で保護すると開けなくなる。段階 3 の申し送りどおりの選択。

スコープは `openid` と `profile` の 2 つ。`openid` がないと ID トークン検証が成立せず、`profile` がないと表示名を取れない。ユーザーの代理でメッセージを送る `chat_message.write` は使わないので選んでいない。

### SDK は CDN から読む

`npm install @line/liff` はしなかった。サーバーサイド HTML に `script` を 1 行足すだけで足りるため、ライブラリを増やさない方針に沿う。SDK が UTF-8 で書かれているため `charset="utf-8"` の指定が要る点は公式が明示している。

LIFF ID は秘密ではないので `wrangler.toml` の `vars` に置いた。`secret` にはしない。

### 実機確認

LIFF ブラウザで開き、初期化の成功、LIFF ブラウザ内であること、ID トークンの取得（712 文字）を確認した。完了条件の「空ページが LINE 内で開く」を満たしている。ID トークンが取れたことで、段階 6 の検証の前提が揃っていることも同時に確認できた。

自動検証で代替できない領域なので、疎通確認ページには初期化の成否と `isInClient()` の結果を画面に出す作りにした。段階 6 ではこの配下にメモ入力と画像一覧を足す。

### 申し送り

LIFF URL は後ろにパスとクエリを足せ、エンドポイント URL と結合されて渡る。段階 5 の応答メッセージに載せる未メモ一覧へのリンクはこの形にできる。

LIFF URL を開いても LIFF ブラウザで開く保証はないと公式が明示している。OS の universal link の仕様に依存するため、段階 6 では外部ブラウザで開かれた場合を考慮する。ログイン状態がないので `withLoginOnExternalBrowser` か `liff.login()` の検討が要る。

受講生に配る前に見直す項目を設計書に残した。チャネル名は初回の同意画面に、LIFF アプリ名は LIFF のヘッダーに出る。いずれも開発者向けの命名（`kouza-app-login` / `kouza-app-memo`）にしてあるため、実際の受講生を入れる前に判断する。プライバシーポリシーと利用規約の URL も現状は空欄で、LINE ユーザー ID・表示名・画像を保存する設計である以上、公開前に用意が要る。

サブエージェントは使っていない。実質的な作業が公式ドキュメントの調査と外部サービスの設定で、コードは疎通確認ページ 1 枚だったため。
