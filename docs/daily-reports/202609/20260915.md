# 2026-09-15

## 講座運営アプリ 段階 5（LINE Webhook で画像を受信し R2 に保存）

設計書 7 章の段階 5 を完了した。トークに送った画像が R2 と D1 に入り、友だち追加で受講生が自動登録され、応答メッセージで LIFF へのリンクが届くところまでを実装し、実機で確認した。PR #11 としてマージ済み。

R2 を有効化して `kouza-app-images` を作り、バインディング名は `BUCKET` にした。D1 の `DB` と同じく、wrangler が提案する長い名前ではなく短い名前を採っている。

### 処理順序が段階 5 の本体

応答メッセージを署名検証の直後、200 を返す前に送る。応答トークンは 1 回限りで、時間制限に依存した実装をしてはならないと公式が明示しているため、画像の取得を挟めない。この順にすると応答時点で画像レコードがまだ無いので、リンクには画像 ID を載せられず LIFF の未メモ一覧へのリンクになる。

follow イベントも同じ扱いにした。当初の計画ではプロフィール取得と UPSERT を応答の前に置いていたが、調査で Webhook のタイムアウトが 2 秒だと分かったため、応答を先に送って残りを `waitUntil()` に逃がした。取得と UPSERT と応答を直列にすると 2 秒に迫る。

### 公式ドキュメントで確認して設計が変わった点

コンテンツ取得だけホストが `api-data.line.me` で、応答メッセージやプロフィール取得の `api.line.me` と違う。公式が明示的に注意書きを置いている箇所で、取り違えると 404 になる。設計書 8 章の表に追記した。

Webhook の再送はデフォルト無効だった。有効化はコンソールの明示操作が要る。今回はオンにしたが、再送は 2xx を返さなかった場合にしか起きないため、正常動作している限り自然には発生しない。

LINE の検証ボタンや疎通確認では `events` が空配列で飛んでくる。固定の replyToken を持つダミーイベントという記載は公式ドキュメント本文には見つからなかった。空配列を 200 で返せば足りる。

### follow に歓迎メッセージを返すことにした

設計書 F1 は follow について自動登録しか書いておらず、応答の有無に言及がなかった。無反応だと登録できたか受講生から見て分からないため、歓迎メッセージを返すことにした。応答メッセージなので課金対象外。

### 表示名は取れたときだけ上書きする

レビューで指摘を受けた。`students` の UPSERT を `ON CONFLICT DO NOTHING` で書くと、`getProfile` が失敗して `(名前未取得)` で行が確定したあと、表示名が二度と入らなくなる。開発者自身には follow が飛ばず最初の行が画像送信の経路でできるため、実際に踏みうる経路だった。

`DO UPDATE SET name = excluded.name WHERE excluded.name <> '(名前未取得)'` として、実名が取れたときだけ上書きする形にした。無駄な API 往復という当初の見立てより深い問題で、レビューを通した価値があった。実機でも `(名前未取得)` から実名への上書きが起きることを本番データで確認できている。

### 型だけ借りるために devDependencies に入れた

`@line/bot-sdk` は設計書の方針どおり `import type` で型だけ借りるが、未インストールでは型解決できないため `devDependencies` に追加した。実行時の依存は増えないので、ライブラリを増やさない方針とは衝突しない。値の import を書くと Node 依存がバンドルされて Workers で動かなくなる。

### 実機確認で 2 度つまずいた

どちらも本番に登録した値が `.dev.vars` と食い違っていたことが原因で、コードの問題ではなかった。

1 度目はチャネルシークレット。全リクエストが署名検証で 401 になり、応答が一切返らなかった。このとき手元に届いていたのは LINE 公式アカウントのあいさつメッセージで、実装した歓迎メッセージではなかった。スクリーンショットを見て文面が違うことに気づき、切り分けが進んだ。

原因特定を遅らせたのは `wrangler tail` の既定の表示で、`- Ok` は「Worker が例外なく応答した」という意味でしかなく HTTP ステータスではない。401 でも `Ok` と出る。`--format json` に切り替えるとレスポンスのステータスが見えて確定した。Webhook が無反応なときは最初からこちらで見る。

2 度目はアクセストークン。署名検証は通るので Webhook 自体は動いて見えるが、`getProfile` が失敗して表示名が `(名前未取得)` のまま入った。ローカルのトークンで直接 API を叩くと 200 が返ったことから、本番側の値が違うと判断した。

どちらも `wrangler secret put` のプロンプトへ手で貼り直すと再発しうる。検証済みの `.dev.vars` からパイプで流し込む形に変えて解決した。

### 自分の検証コマンドが誤っていた

`wrangler r2 object get` に `--remote` を付けていなかったため、実際には保存されているオブジェクトを「存在しない」と誤判定した。ローカルのエミュレート先を見ていたのが理由。CLAUDE.md の検証コマンドの表を修正した。

同じ表に `r2 object list` を書こうとして、そのサブコマンドが存在しないことも実行して分かった（`get` / `put` / `delete` のみ）。保存されたキーの一覧は D1 の `images.r2_key` で見る。

### 申し送り

応答メッセージのリンクは最終形で出しているため、段階 6 で `/liff/images` を実装するまでは 404 に着地する。段階 5 の完了条件はリンクが届くことなので条件は満たしている。

冪等性は実地で確認できていない。再送が 2xx を返さなかった場合にしか起きず、正常動作している限り発生しないため。同じ画像を手で 2 回送っても `line_message_id` が変わるので検証にならない。`images.line_message_id` の UNIQUE と決定的な `r2_key` で担保している状態にとどまる。

本番に残っているのは受講生 1 件（実 ID）、画像 1 件、講座回 1 件。画像の `lesson_id` と `memo_body` は NULL なので、段階 6 の未メモ一覧の絞り込みにそのまま使える。

段階 3 の申し送りにあったテスト行は削除済み。
